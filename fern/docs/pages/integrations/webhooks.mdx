## Webhook structure

Each webhook from Schematic is a `POST` request with a JSON body structured as follows.

```json
{
  "event_id": "whev_xxxxxxxx",
  "action": "<webhook.name>",
  "account_id": "acct_xxxxxxx",
  "environment_id": "env_xxxxxxxx",
  "object_type": "<object>",
  "body": {},
  // if applicable
  "company_id": "comp_xxxxxxxx",
  "feature_id": "feat_xxxxxxxx"
}
```

| Field | Description |
| --- | --- |
| `event_id` | Identifies this delivery of this event to this endpoint. It is the same on every retry, so use it to drop duplicates. It matches the `id` of the event in the webhook log and in `GET /webhook-events` |
| `action` | The webhook event type, e.g. `company.created` |
| `account_id` | The account the event occurred in |
| `environment_id` | The environment within the account the event occurred in |
| `object_type` | The type of object the event relates to |
| `body` | Payload containing event-specific data; shape varies by event type |
| `company_id` | Present on company-scoped and entitlement trigger events |
| `feature_id` | Present on entitlement trigger events |

The contents of `body` vary depending on the event. You can inspect real payloads using free services like [Webhook.site](https://webhook.site) or the webhook log in the Schematic dashboard.

## Signature verification

Every webhook request Schematic sends includes three headers for verifying authenticity, plus two that describe the delivery:

| Header | Description |
| --- | --- |
| `X-Schematic-Webhook-Signature` | HMAC-SHA256 signature of the request body, hex-encoded |
| `X-Schematic-Webhook-Signature-Version` | Signature version — currently `v1` |
| `X-Schematic-Webhook-Timestamp` | Unix timestamp of when this attempt was sent |
| `X-Schematic-Webhook-Id` | Same value as `event_id` in the body, so you can deduplicate before parsing. Only the body is covered by the signature |
| `X-Schematic-Webhook-Attempt` | Which delivery attempt this is, starting at `1` |

The signature is computed as:

```
HMAC-SHA256(secret, rawBody + "+" + timestamp)  →  hex-encoded
```

where `secret` is the webhook secret shown in the Schematic dashboard when you create the webhook endpoint.

Each SDK ships a built-in helper to handle verification for you:

<CodeBlocks>
```typescript title="Node.js"
import { verifyWebhookSignature } from "@schematichq/schematic-typescript-node";

// Express example
app.post("/webhook", express.raw({ type: "application/json" }), (req, res) => {
  try {
    verifyWebhookSignature(req, process.env.SCHEMATIC_WEBHOOK_SECRET, req.body);
  } catch (err) {
    return res.status(400).send("Invalid signature");
  }

  const event = JSON.parse(req.body.toString());
  // handle event...
  res.sendStatus(200);
});
```

```python title="Python"
from schematichq.webhook_utils import verify_webhook_signature, WebhookSignatureError

# Flask example
@app.route("/webhook", methods=["POST"])
def webhook():
    try:
        verify_webhook_signature(request, secret=os.environ["SCHEMATIC_WEBHOOK_SECRET"])
    except WebhookSignatureError:
        return "Invalid signature", 400

    event = request.get_json()
    # handle event...
    return "", 200
```

```go title="Go"
import "github.com/schematichq/schematic-go/webhooks"

func webhookHandler(w http.ResponseWriter, r *http.Request) {
    err := webhooks.VerifyWebhookSignature(r, os.Getenv("SCHEMATIC_WEBHOOK_SECRET"))
    if err != nil {
        http.Error(w, "Invalid signature", http.StatusBadRequest)
        return
    }

    // handle event...
    w.WriteHeader(http.StatusOK)
}
```
</CodeBlocks>

<Warning>Always use your framework's raw body middleware when verifying signatures. Parsed or re-serialized bodies will not match the original signature.</Warning>

## Delivery and retries

Schematic delivers webhooks asynchronously. Your endpoint should acknowledge receipt by responding with any `2xx` status code within 5 seconds. Acknowledge first and do the work afterwards; a handler that processes the event before responding will time out under load.

If your endpoint responds with a non-`2xx` status (anything `300` or above, including `4xx`) or does not respond within 5 seconds, Schematic treats the attempt as failed and retries it. There are up to 8 attempts over about 24 hours, at roughly these offsets from the first:

| Attempt | When |
| --- | --- |
| 1 | immediately |
| 2 | 30 seconds |
| 3 | 5 minutes |
| 4 | 30 minutes |
| 5 | 2 hours |
| 6 | 5 hours |
| 7 | 10 hours |
| 8 | 24 hours |

Each wait is jittered by about 10%. Once the last attempt fails, the event is not delivered again. Disabling or deleting an endpoint drops its pending retries; re-enabling it does not resume them.

Every attempt sends the same body, so `event_id` and the `X-Schematic-Webhook-Id` header are stable across retries. The timestamp and signature are fresh on each attempt.

<Note>Design your handler to be idempotent and key it on `event_id`. An event can arrive more than once, for example when your endpoint processes a request but the response is lost in transit, and a retried event can arrive after newer events for the same object. Do not rely on webhooks arriving in order; compare timestamps in `body` when order matters.</Note>

Test sends from the dashboard are delivered once, are not recorded in the webhook log, and carry no `event_id` or `X-Schematic-Webhook-Id`.

### Endpoint health

If an endpoint fails consistently, Schematic automatically deactivates it so it stops sending to a broken destination. A delivery counts as failing once it has given up, or once it has failed 3 attempts (about 30 minutes) and is still retrying. When 90% or more of at least 25 attempted deliveries in a rolling 24-hour window are failing, the endpoint is deactivated. You can re-enable the endpoint from the webhooks page in the dashboard once the issue is resolved.
