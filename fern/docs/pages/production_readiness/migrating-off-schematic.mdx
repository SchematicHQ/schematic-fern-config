If you decide to move off Schematic, to another vendor or to a system you build yourself, your billing, your flag checks, and your data go with you. This page covers what you keep, what you replace, and how to cut over without your customers seeing a change in billing or in what your app lets them do.

# Your billing stays in Stripe

Your customers, subscriptions, payment methods, and invoices are stored in your own Stripe account. When you disconnect Schematic, Stripe keeps billing your existing subscriptions at their current prices.

Schematic sends a few things to Stripe on your behalf, and each one stops when you disconnect. Put a replacement in place for each before you do:

- Usage that Schematic reports to Stripe for metered prices. Without a replacement, metered charges stop accruing.
- Plan changes, upgrades, and cancellations that customers make through Schematic checkout and the customer portal.

# Keep flag checks running through the cutover

Replacing every flag check in your codebase takes time, and your app has to keep making the same decisions while you do it. Backend SDKs in Replicator mode evaluate flags locally from Redis and never call the Schematic API. Normally the [Replicator](/developer_resources/sdks/cross-platform-features#replicator) container keeps Redis current. During a migration, you restore a final snapshot into Redis instead, and your SDK keeps evaluating flags from it after your account closes, until you replace each check.

Replicator mode is available in the Go, Node.js, Python, Java, and C# SDKs. All Schematic SDKs are MIT licensed, so you can keep running and modifying them after you leave.

To cut over:

1. Take a final snapshot with the `schematic-export` `all` command, described in [Export your data](#export-your-data), before your account closes.
2. Load the snapshot into Redis with the `restore` command.
3. Start the `serve-health` command. It stands in for the Replicator's health endpoint, which tells your SDK the cache is ready and which cache version to read.
4. Run your SDK in Replicator mode against that Redis instance, with `replicatorHealthURL` pointing at `serve-health`.

A restored snapshot behaves differently from a live Replicator in a few ways that change how you plan the cutover:

- Your SDK reads flags, companies, and users from Redis, so you need a Redis instance you control.
- Flag rules, plans, and entitlements stay exactly as they were when you took the snapshot. Make configuration changes in your new system, not in Schematic.
- Usage from `track` calls keeps counting in Redis, but metered limits don't reset at the start of a new period, so a company that hits a monthly limit stays at it.
- Pin your SDK version. The snapshot is stored in the format of the rules engine version it was taken with.
- Client-side SDKs (JavaScript, React, and Vue) call the Schematic API directly, so after your account closes they return flag defaults. Move client-side checks to your new system before then.

Set [flag defaults](/production_readiness/availability) in every SDK, client-side and backend. They decide what your app shows for any flag the snapshot doesn't cover.

# Export your data

`schematic-export` is an open-source CLI that exports your Schematic configuration and usage as JSON, so you can load plans, entitlements, companies, and usage history into your new system. The export reads from the Schematic API, so run your final export while your account is still active.

Clone it from [github.com/SchematicHQ/schematic-export](https://github.com/SchematicHQ/schematic-export), build it with `npm install && npm run build`, and run commands from the repo directory.

| Command | What it does |
|---|---|
| `all` | Runs `config`, `usage`, and `snapshot` together |
| `config` | Exports plans, plan versions and their entitlements, add-ons, features, flags, credits, companies, company overrides, users, and billing product mappings |
| `usage` | Exports events, plus current usage per company for each metered feature |
| `snapshot` | Exports the flag, company, and user data your SDK reads in Replicator mode |
| `restore` | Loads a snapshot into Redis, with no call to the Schematic API |
| `serve-health` | Serves the Replicator health endpoint for a restored snapshot |

Each run writes JSON to a timestamped directory, locally or in S3, and updates `latest.json` to point at it. Every run logs the account and environment it's exporting, so check that line the first time you run with a new key.

```sh
# Export everything while your account is active
node dist/cli.js all --out s3://your-bucket/schematic

# After your account closes, serve flag checks from the last snapshot
node dist/cli.js restore --from s3://your-bucket/schematic --redis redis://localhost:6379
node dist/cli.js serve-health --from s3://your-bucket/schematic --port 8090
```

Create a [readonly secret API key](/api-reference/authentication#readonly-api-keys) for the export. A readonly key can make every request the export needs and can't change anything in your account.

The events API returns about the last six months of events. If you want a longer usage history in your new system, run `all` on a schedule from cron or CI and keep every run, so your archive holds events after they age out of the API. Use `--since` on `all` or `usage` to export only recent events on each run.
