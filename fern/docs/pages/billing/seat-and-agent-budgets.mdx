Credits belong to a company, not to the individual people and agents inside it. A company holds one pool, and every consumption event records the user or agent that caused the draw, so the balance stays shared while consumption is reported per actor.

## Agents are users

Schematic has no separate entity type for autonomous agents. An agent is [identified](/quickstart/identifying-users) as a user on the company, the same as a person, and distinguished by a trait:

```typescript
await client.identify({
  keys: { user_id: "support-bot" },
  name: "Support Agent",
  traits: { actor_type: "agent" },
  company: { keys: { id: "northwind" } },
});
```

That trait is what subsequent behavior keys off. It can be targeted in flag rules to evaluate entitlements differently for agents than for people, used to filter reporting by actor type, and used to price agent seats separately, without maintaining a parallel identity model.

Give each agent its own key rather than sharing one key across a fleet. Attribution is only as granular as the identities you send.

## Scaling the pool to seats

A [credit grant on a plan](/billing/credit-burndown) can be a flat amount per company, or it can scale with the number of licenses the company holds.

Set **Grant Type** to **Scale by license** on the grant and select the license feature that drives it. The grant is then issued once per license the company holds. Enabling **Also grant a flat amount per company** adds a fixed amount once per company on top, producing a base allocation that everyone shares plus a per-seat allocation that grows with the team.

The dashboard controls map to these API fields on the plan credit grant:

| App control | API field | Values |
| --- | --- | --- |
| Grant Type | `scaling` | `fixed` or `per_license` |
| License Feature | `license_id` | The license whose quantity scales the grant. Required when `scaling` is `per_license` |
| Credits per License | `credit_amount` | Integer |
| Flat Amount per Company | `company_credit_amount` | Integer. Only valid when `scaling` is `per_license` |

For example, 2,000 credits per company plus 1,000 per license grants a five-seat company 7,000 credits per period and a ten-seat company 12,000. Both amounts land in the same balance; the customer does not manage two pools.

Scaling by license is a property of a credit grant. Other entitlement values, including usage limits, are set per company and are not multiplied by license count.

Changing the grant type on a plan that companies are already subscribed to re-issues their credits in the new shape and resets any balance they had accrued. The dashboard warns about this at the point of the change.

An agent can hold a license the same way a person can, so an agent seat expands the pool on the same terms. Whether that is the desired behavior is a pricing decision. Agents that consume substantially more than people are usually given their own license type with its own credit amount, rather than sharing the allocation attached to a human seat.

See [Create plan credit grant](/api-reference/billing-credits/create-plan-credit-grant) for the full request body.

## Attributing draws to an actor

A credit draw is attributed to the user identified on the track event. Send `user` alongside `company` and the consumption is recorded against that actor:

```typescript
await client.track({
  event: "inference_tokens",
  company: { id: "northwind" },
  user: { user_id: "support-bot" },
  quantity: 140,
});
```

If `user` is omitted, the draw is still billed to the company correctly, but is recorded as unattributed and counts toward the company total without appearing against any actor. Treat `user` as required on any event caused by a person or an agent.

Attribution is carried through to the [credit ledger](/use-cases/credit-ledger), so ledger entries identify the actor as well as the action.

## Reporting on per-actor consumption

The **Usage by user** table on a company's profile reports the pool broken down by actor. It is in the usage section of the company page, below the Events table, and covers a 7, 30, or 90 day window.

| Column | Contents |
| --- | --- |
| User | One row per user or agent |
| Usage | Consumption for the selected metric, either **Credits** or an individual metered feature |
| Share | That row's fraction of the company's total consumption, with unattributed consumption included in the denominator |
| Last seen | The actor's most recent activity, which identifies agents still drawing after the workflow that owned them was retired |

Summary statistics above the table report total usage, active users, and the highest-consuming user for the window.

## Enforcing a per-actor budget

Enforcement operates on entitlements and on the company balance, not on per-actor caps. No field limits how much of a company's balance an individual user or agent may consume, and nothing stops one actor from drawing the entire pool. A per-actor budget is assembled from the pieces below.

**The pool is the shared ceiling.** A company cannot collectively spend more than it holds. [Auto top-up and bundle purchasing](/billing/spend-controls) determine whether the customer can raise that ceiling themselves.

**Flag rules can gate per user.** A flag check takes both the company and the user, so a rule targeting `actor_type` can grant agents different access than people on the same plan. This is a boolean gate rather than a spend limit, but it can prevent an agent from reaching an expensive code path.

**Holds prevent concurrent overdraw.** When several agents draw on one balance at the same time, [credit holds](/billing/credit-holds) keep them from collectively overdrawing it in the interval between a balance check and a usage report.

**Per-actor consumption is queryable.** A scheduled job can read per-actor consumption and disable an over-budget agent in your own system. This enforces the budget in your application rather than in Schematic, and is not real-time.
